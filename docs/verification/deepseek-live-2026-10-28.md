## 结论

官方 `https://api.deepseek.com`、`deepseek-flash` 真实调用已打通。验证通过本机正常 StoreSpark 服务执行，配置来源为用户保存的服务端配置，没有向工作流注入 MockTransport。模型密钥未写入报告、源码、日志或 GitHub。

修复空标题校验后，共执行 7 次业务请求：6 次 HTTP 200，1 次修改请求未通过输出完整性或 JSON 校验而返回 502；该次输入和原有文案保留，随后显式重试成功。成功请求耗时为 3.82 至 7.99 秒。不能把这些结果写成零失败或业务验收通过。

## 发现并修复的应用问题

澄清阶段没有生成正文，真实模型返回了空 `title`。原有 `ModelReply.title` 无条件要求非空，导致完整 JSON 被应用拒绝。诊断记录确认其余字段类型符合约定。

本次仅改为有正文时才要求非空标题，并同步提示词。无正文的澄清或方向允许空标题；有正文但空标题、未知字段和错误类型仍拒绝，不以容错名义接受坏数据。

新增 4 项 API 回归，旧代码下空标题澄清/方向子场景返回 502；修复后新 4 项与原 46 项共 50 项检查通过。随后重启正常服务，保留原数据与已保存配置，再进行上述真实复验。

## 完整保留的失败边界

修复前执行过两次业务 API 请求，均返回 502，用户输入保留、没有成品。首轮因终端默认编码导致日志输出失败，未保存独立响应详情；状态可由服务日志与任务回读确认，不能倒推出首轮的具体校验错误。第二轮保存了“模型返回内容结构不完整”的响应。

另外进行过两次直接 provider 诊断：一次未通过输出完整性或 JSON 检查，没有取得原始响应；另一次取得完整 JSON，明确定位到空标题。后者记录的供应商模型为 `deepseek-flash`。这两次诊断不写入任务回复，也不计入表格的 7 次业务复验。

因此，本轮助手合计发起 11 次与真实模型有关的调用：修复前业务 2 次、直接诊断 2 次、修复后业务 7 次。没有完整记录全部请求的 token 和实际费用，不估算或声称总费用。失败请求的成功结束标志、空响应和 JSON 解析原因没有全部区分，不能把所有失败归因于同一原因。

完整本地记录保留在忽略的 `test-results/deepseek-live-20261028/` 中；没有删除失败记录，也没有把重试成功写成首次成功。
