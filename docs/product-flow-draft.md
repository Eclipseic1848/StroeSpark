# StoreSpark 产品流程草案

版本：0.1。更新日期：2026-10-26。

产品使用过程拟为：**描述需求或提交素材 → 补充必要信息 → 确定宣传方向 → 生成成品 → 修改 → 交付与验证。**

本稿供项目发起人评审产品设想与实现约束。用户后续已同意按该流程开始代码编写，并于 2026-10-28 要求继续及同步 GitHub，见[GitHub 任务跟踪](github-tracking.md)。首版当前实现为文本与 Markdown，具体渠道及更多成品格式仍待继续收敛。

## 已确认的要求

餐饮优先，服务店主、门店和品牌运营人员。需求明确或模糊、素材充足或零准备都能开始。一次任务交付宣传方向及依据、对应成品、使用与验证建议，目标是让消费者愿意进店尝试。依据见[需求与决策记录](discovery-log.md)。

发起人是 IT 实现人员，可以参与产品与技术取舍；商家事实、偏好和经营效果需要真实反馈验证。

## 建议的使用流程

以下是助手提出的流程，供评审。

| 步骤 | 用户提供或决定什么 | 系统做什么 | 用户拿到什么 |
|---|---|---|---|
| 1 开始任务 | 用一句话描述诉求，或提交菜单、照片、既有宣传内容等素材。 | 从对话和素材中提取已有信息，找出尚不清楚的目标。 | 对本次任务的初步理解，以及必要的补充问题。 |
| 2 说清任务 | 回答自己知道的问题；不知道的可以保留。确认这次想做什么、在哪里使用。 | 只补问影响本次交付的信息。渠道或形式不明确时，提出具体建议供选择；已有明确要求时直接承接。 | 一份简短任务摘要：目标、使用场景、交付物、已有资料和待补信息。 |
| 3 确定方向 | 确认或调整本次宣传的重点。已有方向可以沿用。 | 结合门店资料提出宣传方向，说明想突出什么、依据是什么。如参考公开信息，区分来源事实和分析假设。 | 可理解的宣传方向及理由、待核实事项。 |
| 4 生成内容 | 确认或补充将进入成品的菜品、价格、位置、活动等真实信息。 | 按本次约定的形式生成内容；缺少真实信息时保留待补位置，输出草稿。 | 与本次交付约定一致的内容，以及影响使用的待补清单。 |
| 5 修改内容 | 指出具体问题，例如卖点不准确、文字太多、画面不合适。 | 修改受影响的部分；需求没有变化时沿用已确认的信息。生成失败时说明情况，保留已有输入与结果。 | 可继续评审的修改结果。 |
| 6 交付与验证 | 核实关键事实，确认内容是否可以使用。 | 提供约定的文件、使用说明和小范围验证建议；未补齐的信息继续明确标出。 | 宣传方向、对应成品、使用和验证建议。仍有关键待补项时保持草稿状态。 |

渠道和格式按每次任务确定。多场景、多格式不代表每次生成全部内容，也不代表首版支持清单已经确定。

## 四种起点如何进入流程

| 用户起点 | 建议处理方式 |
|---|---|
| 需求明确，有素材 | 先理解任务并读取素材，只补问会影响交付的缺口。 |
| 需求明确，无素材 | 直接承接目标，区分可以先拟的内容和必须由商家补充的真实信息。 |
| 需求模糊，有素材 | 结合资料帮助用户提出具体宣传任务，再确认本次交付物。 |
| 需求模糊，无素材 | 从经营诉求开始，用少量问题和具体选项帮助收敛；允许先形成方向和草稿。 |

四种起点共用上述流程。具体提问数量、需要补齐的最少资料及沟通负担，需要通过使用反馈确定。

## 内容使用前的边界

- **真实信息**：零准备可以开始。涉及菜品、价格、地址、优惠及有效期等内容，使用前需要商家核实；系统不能补造事实。
- **素材使用**：能上传哪些文件、如何确认使用权限、保存多久及如何删除仍待设计；用户提供的素材不自动成为对外公开内容。
- **公开信息**：来源、时效、可访问性及分析价值仍待验证。无法取得可靠资料时，明确依据不足，可以继续讨论假设，不能声称已掌握消费者心智。
- **成品标准**：与约定交付物逐项对应。脚本、分镜和视频成片分别计算；内容能预览或商家觉得好看，不代表已满足实际使用要求。具体尺寸、格式和质量门槛仍待确定。
- **效果验证**：区分商家愿意采用、制作时间与修改负担、消费者反馈和实际进店行为。先给验证建议，不承诺转化提升。

## 蒸饺店案例如何开始

走查开场可以是：“我在江苏开了一家东北蒸饺店，想让附近的人愿意来试试，不知道怎么宣传。”这句话根据已有案例改写，用于解释流程，并非商家原话。

系统先了解内容准备在哪里使用、是否有可用门店资料。商家不清楚渠道时，给出具体选择及理由；没有资料时，先拟方向并列出待补信息。确定本次交付物后，再制作相应内容。海报可以作为讨论选项，不能据此认定商家需要海报或首版只做海报。

## 下一轮需要讨论什么

先由发起人评审上述流程是否符合产品设想，有无遗漏或多余环节；再结合可获得的商家反馈与实现约束，提出首版场景、渠道和格式的候选范围。自动发布、广告投放、代运营的范围仍未定。

商家反馈重点包括：最想完成的实际任务、对现有产物不满意的具体表现、愿意提供哪些资料，以及什么样的结果可以采用。发起人不了解的答案保留待验证。

后续已实现 Python API 与 Web 工作台，并选择官方 DeepSeek Flash；具体进度以 GitHub 任务跟踪和交接说明为准。此处的流程建议仍不能替代商家需求、质量标准与经营效果验证；候选 Skill 和开发工期尚未确定。
